The two ways across

Almost every mistake on this page comes from knowing only the first of these.

1 — move yourself right Raise arithmetic intensity: reuse loaded tiles across more output (blocking), cut bytes per element (bfp8), or fuse ops so one load feeds more arithmetic. This is the only lever that changes what your algorithm is.

2 — move the ridge left ridge = peak ÷ bandwidth. Raising achieved bandwidth — sharding, multicast, operands resident in L1 — lowers the ridge and can bring it under you without your kernel changing at all.

Everything else — core count, batching, CB depth, problem size — moves you vertically, up toward whichever roof you are already beneath. Necessary work, but it never changes which roof that is.

And note the trap in the other direction: more cores and lower fidelity both raise peak, which pushes the ridge right and makes you more memory-bound, not less.
