Reading a CCL Call

Every argument on ttnn.all_gather answers a different question, and they live in three separate coordinate systems. Once you know which register an argument belongs to, the call reads itself.

The frame

Three registers, not one list of options

The reason a CCL call looks confusing is that its arguments are drawn from three different spaces that all happen to use the word "dimension" or "axis." Sort them once and they stop colliding.

Tensor space Which numbers move? mesh_mapper's dim
dim=
Mesh space Which chips talk to each other? cluster_axis=
Wire space How do the bytes get there? topology=
num_links=

The single most common mix-up: dim indexes the tensor (0…3 for a 4-D tensor). cluster_axis indexes the mesh (0 or 1 for a 2-D mesh). In all_gather(t, dim=3, cluster_axis=1) the two numbers have nothing to do with each other.

Sharding is not in any of these

How the tensor was split across chips is fixed earlier, by the mesh_mapper you passed to ttnn.from_torch. No CCL argument changes it. topology and num_links never touch data placement at all — they only describe the wires the op is allowed to run over.

Worked example

One tensor, eight chips

Everything below uses the same setup: a [1, 1, 32, 256] tensor on a 2×4 mesh, width-sharded.

mesh_device = ttnn.open_mesh_device(ttnn.MeshShape(2, 4))
t = ttnn.from_torch(
    torch.rand((1, 1, 32, 256)),
    layout=ttnn.TILE_LAYOUT, device=mesh_device,
    mesh_mapper=ttnn.ShardTensorToMesh(mesh_device, dim=3),   # 256 / 8 = 32 per chip
)

The mapper walks the mesh in row-major order and hands each chip a [1, 1, 32, 32] slice:

Mesh space

cluster_axis — who is in the conversation

A CCL op is a conversation among a set of chips. cluster_axis names the mesh dimension you travel along, which in turn decides how many independent conversations run at once.

What each choice yields for our tensor

cluster_axisGroupDevices per groupall_gather(dim=3) output per chip
0a column2[1,1,32,64] — 4 distinct results, one per column
1a row4[1,1,32,128] — 2 distinct results, one per row
Nonethe whole mesh8[1,1,32,256] — identical on every chip
Two things to know about None

On a 2-D mesh with a 1-D fabric, all_gather refuses to run without an explicit cluster_axis: "1D fabric on a 2D mesh_device requires cluster_axis to be set".

And for reduce_scatter / all_reduce, passing None on a non-1×N mesh is not one flat 8-device collective — it silently decomposes into a pass on cluster_axis=1 followed by a pass on cluster_axis=0.

Wire space

topology — whether the chain closes

Once cluster_axis has picked a line of chips, topology says whether that line has a wraparound link joining its two ends. That one edge is the entire difference.

Ring is a request, not a guarantee

Passing topology=ttnn.Topology.Ring does not fail when the wraparound doesn't exist — the op resolves it against the hardware and silently downgrades to Linear. Two rules decide it: an axis of extent 2 never wraps, and without a cluster_axis the device set must span the whole mesh.

On our 2×4 mesh that means only cluster_axis=1 can actually be a ring. cluster_axis=0 has extent 2, and cluster_axis=None is disqualified because mesh dimension 0 is 2. You can check what you'll really get before running anything:

ttnn.get_usable_topology(t, cluster_axis=1)   # -> Topology.Ring
ttnn.get_usable_topology(t, cluster_axis=0)   # -> Topology.Linear  (extent 2)

So don't hardcode it. In model code, ask the config:

# models/tt_transformers/tt/model_config.py:2521
topology = model_args.ccl_topology()   # Ring on T3K/Galaxy at >=8 devices, else Linear

Wire space

num_links — how many cables in parallel

Adjacent chips are joined by more than one ethernet link on most boards. num_links is how many of them the op may use at once. It is a bandwidth dial, never a correctness one — the same payload is divided across the links, not duplicated and not increased.

Putting it together

The three ops, in terms of chip state

Think of each chip's tensor as being in one of three states, and the ops as transitions between them. Fractured means each chip holds a distinct slice. Partial means each chip holds a full-size tensor that is only part of the sum. Gathered means every chip in the group holds the same complete result.

OpInOutOn our board, cluster_axis=1
all_gatherfracturedgathered [1,1,32,32] → [1,1,32,128], 4× the memory
reduce_scatterpartialfractured, reduced [1,1,32,32] → [1,1,32,8], summed over the row
all_reducepartialgathered, reduced [1,1,32,32] → [1,1,32,32], summed over the row

all_reduce is currently a composite of reduce_scatter then all_gather — which is why the two-pass cluster_axis=None behaviour applies to it too.

Where each one shows up in a transformer

  • Column-parallel matmul (weights split by width): output is fractured, so an all_gather on dim=3 puts the full activation back on every chip.
  • Row-parallel matmul (weights split by height): output is partial, so a reduce_scatter — or a full all_reduce if the next op needs it gathered.
  • 2-D weight sharding on a 2-D mesh: reduce along cluster_axis=1 first, then gather the shards along cluster_axis=0. Two calls, two different axes — the clearest case for keeping mesh space and tensor space apart in your head.
Errata

Where the tech report has drifted

tech_reports/LLMs/llms.md §3.3 is still the right place to start, but three details no longer match the code. Worth knowing before you take a number from it.

llms.md saysCurrent state
:1232 — TG has 4 links on axis 0, 3 on axis 1 The link table gives TG (4, 4). Query get_num_links instead of quoting either.
:1245 — a Ring all-gather over all 8 chips of a 2×4 mesh, no cluster_axis Mesh dimension 0 is 2, so the wraparound is rejected and this resolves to Linear. A 1-D fabric would reject the missing cluster_axis outright.
:1348 — data-movement table, "Ring results in less overall data movement" The printed formulas say the opposite. At D=8 the Line row gives 7S and the Ring row gives 24S; the log₂ term looks borrowed from recursive doubling. Trust the direction (Ring wins), not the arithmetic.
In practice

Reading any CCL call in four questions

  1. What shape is on each chip right now? That comes from the mesh_mapper, not from anything in this call.
  2. cluster_axis — which chips talk? Axis 0 is columns of the mesh, axis 1 is rows. The group size is the mesh extent along that axis; everything outside the group keeps its own separate result.
  3. dim — which tensor dimension grows or shrinks? Unrelated to the mesh. For width-sharded activations this is nearly always 3.
  4. topology and num_links — how fast? Neither changes the answer, only the time to get it. Resolve both from helpers so a submesh or a different board doesn't quietly cost you performance.
The habit worth forming

Write model_args.ccl_topology() and get_num_links(mesh_device, cluster_axis) rather than literals. Both already encode the per-board rules, and both keep working when the same model runs on an N300, a T3K row, and a Galaxy submesh.

Line numbers refer to tenstorrent/tt-metal and were current when this page was written; treat them as pointers, not permalinks.
